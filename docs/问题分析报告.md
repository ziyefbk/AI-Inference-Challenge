## 项目概述

这是一个竞赛推理服务，架构如下：

```
main.py
  ├── vLLM 推理引擎（后台进程，端口 8000）
  ├── HTTP 健康检查服务器（端口 9000）
  └── 调度客户端循环（后台线程）
       ├── register()       — 向平台注册
       ├── query_task()     — 查询任务
       ├── accept_task()    — 领取任务
       ├── run_inference()  — vLLM 推理
       └── submit_results() — 提交结果
```

支持三种任务类型：

| 任务类型 | eval_request_type | vLLM API | 计算内容 |
|---|---|---|---|
| 文本生成 | `generate_until` | Completions | 完整文本响应写入 `response` |
| 条件概率 | `loglikelihood` | Completions | log P(continuation \| prompt) 写入 `accuracy` |
| 滚动概率 | `loglikelihood_rolling` | Completions | 整文档总 logprob 写入 `accuracy` |

## P0 — 严重问题

### P0-1: 优先级计算公式方向完全反向

**文件**: `src/client/task_holder.py` 第 37-63 行

```python
def _compute_priority(self, task: Dict[str, Any], accept_time: float) -> float:
    # ...
    remaining = deadline_ms / 1000.0 - time.monotonic()
    # ...
    priority = remaining * urgency_weight + complexity_penalty - reward_factor + sla_adjustment
```

**问题分析**:

- `heapq` 是最小堆，`priority` **越小越优先**
- 当前公式中，`remaining` **越大** priority 越大 → 剩余时间越多反而越优先（紧急任务被后排）
- `reward_factor = reward * 20 / remaining`，符号为负 → 高奖励反而让 priority 变大（更不优先）
- `sla_adjustment` 中 express=-50、fast=-20、standard=0、high_quality=10，方向是对的（紧急任务优先级更高），但被其他反向项抵消

**实际影响示例**:

假设两个任务：

| 任务 | remaining | complexity | reward_factor | sla_adj | priority |
|---|---|---|---|---|---|
| express 任务（60s 后到期） | 60 | 3 | 10 | -50 | **1.0** |
| standard 任务（5s 后到期） | 5 | 0.6 | 25 | 0 | **-20.4** |

standard 任务 priority=-20.4（更小），被优先处理——deadline 更近的 express 任务反而被后排。

**正确思路**: priority 应该是 deadline 越近越低、奖励越高越低。修复方向：

```python
# 修复: 取负值使 deadline 越近 priority 越低，高奖励使 priority 更低
priority = (
    -remaining * urgency_weight          # 剩余时间越少越紧急 → priority 越低
    - reward * reward_weight             # 奖励越高越优先 → priority 越低
    + complexity_penalty                 # 越复杂 penalty 越大
    + sla_adjustment                    # express=-50 使 priority 更低
)
```

### P0-2: `loglikelihood_rolling` 设置 `max_tokens=1` 导致 perplexity 计算错误

**文件**: `src/inference/task_types/loglikelihood.py` 第 85-124 行

```python
async def compute_rolling_logprob(text: str) -> float:
    resp = await completions(
        prompt=text,
        max_tokens=1,         # <-- BUG: 只生成 1 个 token
        logprobs=1,
        temperature=0.0,
        top_k=1,
        echo=True,            # 返回所有 token 的 logprob
    )
    # ...
    valid = [float(lp) for lp in lp_list[1:] if lp is not None]
    total = float(sum(valid)) if valid else -10.0
```

**问题分析**:

1. **缺失第一个 token 的 logprob**: `lp_list[0]` 永远是 `None`（第一个 token 没有前驱），`lp_list[1:]` 从第二个 token 开始提取。但第一个 token（`token_0`）的 logprob 永远缺失，导致 perplexity 系统性偏低
2. **长文档可能 OOM**: 对整篇文档做 prefill 需要为每个 token 分配 KV cache，`max_tokens=1` 只生成 1 个新 token 但 prefll 整个 prompt，在文档很长时可能导致 CUDA OOM
3. **vLLM 行为不确定**: vLLM 在 `echo=True` + `max_tokens=1` 时的行为可能因版本而异，不应依赖这种边界用法

**正确思路**: 应使用 `max_tokens=0` 触发纯 prefill 模式，或者考虑 vLLM 的专用 perplexity 接口。

### P0-3: `_check_counter` 共享状态被多个 worker 无序累加

**文件**: `src/client/loop.py` 第 116-136 行 + `src/client/task_holder.py` 第 116-123 行

**loop.py 中的累加**:

```python
async def inference_worker(worker_id: int):
    while True:
        item = await task_holder.pop_task()
        if item is None:
            task_holder._check_counter += 1  # 所有 worker 共用同一个 counter
            if await task_holder.should_check_expired():
                expired = await task_holder.get_expired()
                # ...
            task_holder._check_counter = 0   # 检查后清零，但时机不对
```

**task_holder.py 中的判断**:

```python
async def should_check_expired(self) -> bool:
    fill_ratio = len(self._heap) / max(self.max_held, 1)
    if fill_ratio > 0.7:
        return True
    elif fill_ratio > 0.4:
        return self._check_counter >= 3
    else:
        return self._check_counter >= 5
```

**问题分析**:

1. **触发时机取决于 worker 数量而非等待时间**: 3 个 worker 各等了 1 次 None → `_check_counter=3` → 立即触发；1 个 worker 等了 3 次 → 同样触发。前者只过了 ~0.05s，后者过了 ~0.15s，但触发条件完全一样
2. **清零时机在检查后而非检查前**: 检查后清零意味着下次仍需等够 N 次才能再检查，但 worker 数量变化会导致清零频率不稳定
3. **并发安全问题**: `pop_task` 是 async 协程，不持有锁，`_check_counter += 1` 虽然是 Python 整数操作（GIL 保护），但语义上不应该在 worker 协程中直接修改 holder 的内部状态

**正确思路**: 过期检查应该是 holder 的职责（基于时间而非计数），或者使用独立的计时器触发，不应该由 worker 轮询计数。

### P0-4: `generate_until` 硬编码 `logprobs=0` 完全放弃 logprobs

**文件**: `src/inference/task_types/generate_until.py` 第 136-149 行

```python
resp = await completions(
    prompt=prompt,
    max_tokens=max_toks,
    temperature=p["temperature"],
    # ... 其他参数完整传递
    logprobs=0,     # <-- 始终禁用 logprobs
)
```

同时 `vllm.py` 中的 `completions` 函数完整支持 `logprobs` 参数，但在 `generate_until` 调用处被硬编码为 0。

1. **功能丧失**: 如果平台需要对生成结果做 token 级别的置信度分析，当前代码无法提供
2. **影响 beam search 选优**: `best_of > 1` 时，logprobs 是选择最佳候选的必要数据。当前所有参数都正确传递，唯独 `logprobs=0` 阻断了这一能力
3. **不对称的 API 使用**: `generate_until` 注释说"使用 completions API 直接生成文本，避免 chat 格式干扰 stop 条件"，但却没有充分利用 completions API 的 logprobs 能力

## P1 — 功能性问题

### P1-1: 多卡 GPU 下 vLLM 只启动 1 个实例

**文件**: `main.py` 第 143-145 行

```python
num_instances = 1          # <-- 硬编码为 1
tp_size = num_gpus
logger.info(f"检测到 {num_gpus} 张 GPU, 启动 1 个 vLLM 实例, TP={tp_size}")
```

**问题分析**:

- `nvidia-smi` 正确检测了 GPU 数量（假设为 4）
- `tp_size = 4` — 每实例使用 4 卡 tensor parallel
- 但 `num_instances = 1` — 只启动 1 个实例

这意味着：4 卡机器用 TP=4 只跑了 1 个实例，GPU 利用率约 25%（4 卡共享一个推理管道）。而 `vllm.py` 的 `_build_vllm_urls` 支持多实例：

```python
def _build_vllm_urls() -> List[str]:
    n = int(os.environ.get("VLLM_NUM_INSTANCES", "1"))
    return [f"http://localhost:{8000 + i}" for i in range(n)]
```

但 `main.py` 从未设置 `VLLM_NUM_INSTANCES`，导致即使支持多实例也无法生效。

**正确思路**: 应根据 GPU 数和每实例 TP size 计算实例数。例如 4 卡机器如果每实例 TP=1，则可启动 4 个实例；如果 TP=2，则可启动 2 个实例。

### P1-2: `estimate_task_feasible` 过于宽松且 `buffer_factor` 从未使用

**文件**: `src/client/task_holder.py` 第 166-185 行

```python
def estimate_task_feasible(task: Dict[str, Any], sla_level: str, buffer_factor: float = 1.3) -> bool:
    """
    策略：极度宽松。只要死线还没到就接受。
    理由：SLA 超时提交 = 不得分不扣分，拒绝 = 必定扣分。
    """
    deadline_ms = task.get("overview", {}).get("deadline_ms")
    if deadline_ms is None:
        return True
    remaining = deadline_ms / 1000.0
    if remaining <= 0.5:
        return False
    return True  # <-- 几乎所有任务都返回 True
```

**问题分析**:

1. **`buffer_factor` 参数存在但从未使用**: 函数签名接受 `buffer_factor` 但在函数体内零引用
2. **任务复杂度完全忽略**: 10 个消息的任务和 1 个消息的任务被同等对待，如果 deadline 只有 1s，两个都接受
3. **deadline 语义不清晰**: 如果 `deadline_ms` 是绝对时间戳（如 Unix 毫秒），应该用 `deadline_ms / 1000.0 - time.time()` 或 `time_monotonic()` 差值，而不是直接比较
4. **注释与实际策略矛盾**: 注释说"宁可超时完成也不提前拒绝"，但这在 deadline=0.1s 时是不现实的——推理本身至少需要几十毫秒

### P1-3: URL 轮询计数器非线程安全

**文件**: `src/inference/vllm.py` 第 53-56、101-104、186-189 行

```python
_url_index = 0

def _get_next_url() -> str:
    global _url_index
    urls = get_vllm_urls()
    return urls[_url_index % len(urls)]

# 在 chat_completions 和 completions 中:
global _url_index
chosen_url = urls[_url_index % len(urls)]
_url_index += 1    # <-- GIL 保护整数操作，但 get_vllm_urls() 可能被并发修改
```

**问题分析**:

1. `get_vllm_urls()` 每次调用会重新读取环境变量并构建列表（如果 `VLLM_URLS` 环境变量在运行期间被修改，行为不可预期）
2. `+=` 操作虽然被 GIL 保护，但在多线程/多协程并发时，URL 分配可能不均匀（某些 URL 被频繁选中）
3. `get_vllm_urls()` 没有被缓存，每次都重新构建

**正确思路**: 使用 `threading.Lock` 保护 `_url_index` 递增，或使用 `asyncio.Lock` 在 async 层面保护。

### P1-4: token 数用 word count 估算，中文误差可超 100%

**文件**: `src/inference/task_types/loglikelihood.py` 第 32-40 行

```python
resp = await completions(
    prompt=prompt,
    max_tokens=len(continuation.split()),  # <-- 用空格分割估算 token 数
    logprobs=1,
    temperature=0.0,
    top_k=1,
    echo=True,
)
```

**问题分析**:

| 语言 | 估算方式 | 实际 token 数 | 误差 |
|---|---|---|---|
| 英文短句 | 空格分词 ~5 词 | ~7 tokens | +40% |
| 英文长句 | 空格分词 ~50 词 | ~65 tokens | +30% |
| 中文 | 空格分词 = 字数 | 实际 tokens | **取决于分词器，可能差 50-200%** |

如果 `max_tokens` 远小于实际需要，会导致 vLLM 在生成指定 token 后截断，`logprobs` 中缺少 continuation 末尾 token 的 logprob。

**正确思路**: 使用 `tiktoken` 或 vLLM 的 tokenizer 精确计算 token 数。

### P1-5: `close_vllm_client()` 在已有事件循环中静默失败

**文件**: `src/inference/vllm.py` 第 285-290 行

```python
def close_vllm_client() -> None:
    """同步关闭 vLLM 客户端。"""
    try:
        asyncio.run(close_all_clients())
    except RuntimeError:
        pass    # <-- 静默忽略，在已有事件循环中调用时客户端永远不关闭
```

**问题分析**:

- `asyncio.run()` 内部会创建新的事件循环，如果当前已有运行中的事件循环（如在 async 上下文中调用），会抛出 `RuntimeError: asyncio.run() cannot be called from a running event loop`
- `except RuntimeError: pass` 静默忽略了这一错误，导致 httpx 客户端的连接永远不关闭
- 在 `main.py` 的 `finally` 块中调用 `close_vllm_client()`，此时主线程可能没有运行中的事件循环，但如果在某个 worker 协程的上下文中调用，问题就会出现

## 关键症状专项分析：大量 ASL（Accept）、零 Submit

> 症状：平台端显示大量任务被 Accept，但零任务被 Submit。

### 完整数据流

```
平台 query() ──→ accept() ──→ task_holder.add_task()
                                        │
                              inference_worker.pop_task()
                                        │
                              process_task(client, task, ...)
                                        │
                              run_inference_async(messages, ...)
                                        │
                              submit_results(client, task_data, ...)
                                        │
                                    返回 True/False
```

每一步都可能出错导致 "零 submit"。

### 根因 1（P0-CRITICAL）：`_submit_breaker` 触发阈值仅为 5

**文件**: `src/client/platform.py` 第 97 行

```python
_submit_breaker = CircuitBreaker(name="submit", failure_threshold=5, timeout=120.0)
```

**致命设计**: submit 熔断器的 failure_threshold 仅 5。

- 只要 **任意 5 次** submit 请求连续失败（429/500/网络错误），熔断器立即打开
- 熔断器打开后，`submit_results` 的开头检查：

```python
async def submit_results(...):
    if not await _submit_breaker.can_attempt():   # 熔断打开时返回 False
        # 触发一次每 10s 的警告日志（不会打印堆栈）
        return False                               # <-- 静默返回 False，不重试

    for attempt in range(max_retries):              # 重试逻辑在熔断检查之后
        # ... 永远不会执行到
```

- **关键**: 熔断器检查在重试循环 **之前**，一旦打开，**所有后续提交全部静默跳过**
- `_submit_breaker.timeout = 120s`，意味着熔断打开后 120s 内所有 submit 都直接返回 False
- `record_success_sync()` 只在 HTTP 200 时调用，如果前 5 次都是 500/网络超时，熔断立即打开

**结论**: 如果竞赛初期有任何提交失败（如 vLLM 刚启动时推理错误、平台短暂不可用），触发 5 次失败后熔断打开，**之后所有任务都进不了 submit**，表现为 "大量 ASL、零 submit"。

**对比其他熔断器**:
| 熔断器 | failure_threshold | timeout | 风险 |
|---|---|---|---|
| `_query_breaker` | 15 | 30s | 低：query 失败通常短暂 |
| `_ask_breaker` | 10 | 60s | 中：任务领取失败需关注 |
| `_submit_breaker` | **5** | 120s | **极高：几乎必然触发** |

### 根因 2（P0-CRITICAL）：`process_task` 中 `run_inference_async` 异常静默吞没

**文件**: `src/client/platform.py` 第 315-347 行

```python
async def process_task(client, task, backoff, sla_level) -> bool:
    messages = task.get("messages", [])
    if not messages:                        # 空消息 → 返回 False
        logger.warning("process_task_empty_messages")
        return False

    results = await run_inference_async(messages, sla_level=sla_level, deadline_ms=deadline_ms)

    log_inference(task_id, messages, results, sla_level)

    task_data = {...}
    return await submit_results(client, task_data, backoff)
```

**问题**: `run_inference_async` 是 `async` 协程，如果在调用链中抛出未捕获异常：

1. 异常向上传播到 `inference_worker`
2. `inference_worker` 的 `asyncio.gather` 用 `return_exceptions=True`，所以协程不会崩溃
3. 但 `process_task` 如果是直接 `await`，异常会在 worker 的协程栈中传播，导致 `process_task` 调用失败
4. 此时既没有调用 `submit_results`，也没有任何错误日志

**实际场景**: 如果 `prepare_sla` 或 `get_adaptive_sla_strategy` 抛异常（如 SLA_LEVELS 为空），整个推理会静默失败。

**额外风险**: `_process_all_async` 中的异常处理只覆盖单条消息级别的错误——如果 `asyncio.gather` 中某几个任务失败，它们会被替换为 error 结果。但如果整个 `_process_all_async` 本身抛出异常（如 semaphore 超时），异常会穿透 `process_task` 到达 worker。

### 根因 3（P1）：`sla_level` 从 `target_sla` 直接透传，可能与内部策略不兼容

**文件**: `src/client/platform.py` 第 337 行

```python
results = await run_inference_async(messages, sla_level=sla_level, deadline_ms=deadline_ms)
```

`process_task` 中的 `sla_level` 来自 `overview.get("target_sla")`（平台下发），直接透传给 `run_inference_async`。

`run_inference_async` 调用的链路：

```
run_inference_async(messages, sla_level=target_sla, ...)
  └── prepare_sla(messages, sla_level=target_sla, deadline_ms)
        └── SLA_LEVEL_TO_STRATEGY = {"Bronze": "standard", "Silver": "standard", ...}
              └── get_adaptive_sla_strategy(deadline_ms, msg_count, effective_sla)
                    └── get_sla_from_deadline(deadline_ms, estimated_duration, msg_count)
                          └── SLA_LEVELS.get(base_sla, {})  # <-- 如果 base_sla 不在 SLA_LEVELS 中...
```

`SLA_LEVELS` 在 `strategy.py` 中有默认值：

```python
SLA_LEVELS = {
    "express": {"ttft_avg": 0.5},
    "fast": {"ttft_avg": 2.0},
    "standard": {"ttft_avg": 5.0},
    "high_quality": {"ttft_avg": 15.0},
}
```

如果平台下发的 `target_sla` 是 "high_quality"（对应 `SLA_LEVELS["high_quality"]`），能正常找到。但如果平台使用任何不在这 4 个 key 中的值，`SLA_LEVELS.get(base_sla, {})` 返回空字典，`get_sla_from_deadline` 中的排序逻辑会出问题，最终可能导致 `max_gen_toks=100000`（strategy 第 71 行的硬编码兜底值）——生成 10 万 token，这会导致 vLLM 请求超时。

### 根因 4（P1）：`loglikelihood` 的 logprob 计算逻辑错误

**文件**: `src/inference/task_types/loglikelihood.py` 第 58-82 行

```python
prompt_len = None
for i, lp in enumerate(lp_list):
    if lp is not None:
        prompt_len = i    # <-- BUG: 找第一个非 None 作为 prompt 长度
        break

# ...

for i in range(prompt_len + 1, len(lp_list)):   # <-- 从 prompt_len+1 开始
    cont_logprobs.append(float(lp_list[i]))
```

**问题**: 这个启发式算法假设"第一个非 None 的 logprob 就是 prompt 最后一个 token"。但 vLLM 的 `echo=True` 行为是：

- `lp_list[0]` = None（第一个 token 没有前驱）
- `lp_list[1:]` = 第一个 token 开始的 logprob

如果 prompt 以空格或特殊 token 开头，`lp_list[0]` 可能是 None，`lp_list[1]` 才是第一个有效 logprob——但这并不意味着 `i=1` 就是 prompt 的末尾。

**实际影响**: continuation 的 logprob 累加范围可能包含部分 prompt token 或遗漏部分 continuation token，导致 logprob 不准确。但如果 vLLM 返回格式恰好对齐，代码可能 "碰巧" 工作。

### 根因 5（P2）：提交数据格式不明确

**文件**: `src/client/platform.py` 第 278-281 行

```python
resp = await client.post(
    f"{PLATFORM_URL}/submit",
    json={"user": {"name": TEAM_NAME, "token": TOKEN}, "msg": task_data},
    timeout=60.0,
)
```

`task_data` 的结构：

```python
task_data = {
    "overview": overview,
    "messages": results,
    "sla_level": sla_level,
}
```

`results` 是 `_aggregate_task_results` 的输出，结构如下：

- 单条消息：`{"ID": ..., "prompt": ..., "eval_request_type": ..., "response": ..., "accuracy": ..., ...}`
- 多条消息聚合后：`{"ID": ..., "response": ..., "accuracy": ..., "message_count": ..., "accuracy_count": ..., ...}`

如果平台期望的字段名是 `task_id` 而代码用的是 `ID`，或者期望 `result` 而不是 `messages`，提交会静默失败。

### 根因汇总：为什么是 "ASL" 而不是直接失败

| 步骤 | 可能失败点 | 对应症状 |
|---|---|---|
| `query_task()` | 熔断打开 | query 减少但不一定 ASL |
| `accept_task()` | 熔断打开/任务被抢 | ASL 减少 |
| `run_inference_async()` | 异常/vLLM 超时 | **推理挂起** |
| `submit_results()` | **熔断打开** | **submit 为 0** ← 主要原因 |
| `process_task()` | 返回 False | submit 为 0 |

**最可能的直接原因**: `_submit_breaker` 在竞赛初期被触发（vLLM 启动期间推理错误、平台瞬时不可用等），熔断打开，之后所有任务都跳过 submit。表现为 "大量 ASL、零 submit"。

**次可能原因**: `run_inference_async` 整体挂起（semaphore=0 或 vLLM 无响应），所有 worker 阻塞，无法触发 submit。

### 诊断建议

1. **查看 `_submit_breaker` 状态**：日志中是否出现 "submit_circuit_open" 警告（每 10s 一次）
2. **查看熔断器状态**：日志中每 10 个任务输出一次 `circuit_breaker_states`，`_submit_breaker` 是否为 "open"
3. **查看 vLLM 响应**：推理请求是否超时（120s），日志中是否有 "chat_retry" 或 "completions_retry"
4. **查看提交响应码**：平台返回 200 才有 `record_success_sync()`，否则熔断持续计数
5. **检查 `_submit_breaker.failure_threshold`**：当前为 5，极易触发，应提高
